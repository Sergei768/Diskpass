# Diskpass

Генератор криптографически защищённых физических тегов для носителей информации.

Diskpass решает конкретную задачу: у вас есть архив из десятков физических носителей (HDD, SSD, LTO-ленты, флешки), и вам нужно как-то подписать каждый из них, не раскрывая посторонним, что на нём находится, чем оно зашифровано и какой пароль от него защищает.

Программа генерирует короткий тег вида `HK-T1R-BAM-LK-XYQ`, который наклеивается на носитель. Владелец, зная схему своей базы, может по этому тегу восстановить тип носителя, объём, содержимое, метод шифрования и найти соответствующую запись с паролем в локальной базе данных. Для всех остальных это просто набор символов.

## Модель нарушителя

Diskpass проектировался под конкретную модель нарушителя (threat model), и важно чётко очертить её границы, а не полагаться на security through obscurity как единственную линию защиты.

**Рассматриваемый противник:** пассивный наблюдатель, обладающий физическим доступом к носителю и нанесённому на него тегу (изъятие, кража, случайная утечка архива), но не обладающий секретным материалом базы — приватным OpenPGP-ключом, паролем к нему, значениями `noise_key` и `salt`. Предполагается, что такой противник может:

- визуально изучить произвольное число тегов на разных носителях из архива;
- пытаться выявить закономерности в структуре тега методом частотного и структурного анализа (сопоставление длин блоков, повторяющихся символов, статистики позиций);
- располагать неограниченным временем на анализ, но не обладать доступом к зашифрованной базе или её ключевому материалу.

**Гарантии в этой модели:**
- Раскрытие семантики тега (тип носителя, объём, метод шифрования, содержимое) невозможно без знания схемы конкретной базы — сама перестановка блоков является частью секрета и не выводима из внешнего вида тега.
- Структурный криптоанализ по нескольким тегам одной базы не даёт противнику информации, достаточной для восстановления словарей кодирования или порядка блоков: замыкающий символ каждого блока — это криптографическая соль (BLAKE2b от значения блока, `noise_key` и `salt`), которая делает статистику блоков неотличимой от равномерного распределения без знания секретного материала.
- Тег без доступа к базе — это short-lived, self-contained артефакт: вне контекста зашифрованной базы он не несёт вычислительно извлекаемой информации.

**Явно вне модели угроз (out of scope):**
- Активный противник, скомпрометировавший приватный ключ и пароль к нему, — при обладании полным ключевым материалом база расшифровывается штатно; Diskpass не защищает от компрометации самого ключа.
- Diskpass не является средством шифрования данных на носителе — это инструмент каталогизации метаданных о методе и параметрах шифрования, уже применённого другим средством (LUKS, VeraCrypt, BitLocker и т. д.).
- Атаки через побочные каналы (side-channel), кейлоггинг, компрометация рабочей станции, на которой выполняется расшифровка базы, — вне периметра ответственности приложения.

Иными словами, устойчивость тега опирается не на секретность алгоритма кодирования (он открыт и описан ниже), а на криптографическую стойкость соли блока и на то, что секретный материал (`noise_key`, `salt`, приватный ключ) существует исключительно внутри OpenPGP-зашифрованной базы и никогда не покидает её в открытом виде.

## Ключевые возможности

- **Генерация физических тегов** из 5 компонентов: тип носителя, объём, пользовательская метка содержимого, метод шифрования, соль диска.
- **Уникальная схема на базу** — при инициализации новой базы порядок 5 компонентов тега случайным образом переставляется (5! = 120 вариантов) и фиксируется как часть секрета базы. Знание формата одной базы не даёт возможности интерпретировать теги другой.
- **Список размеров зависит от типа носителя** — при выборе, например, LTO5 в форме добавления записи предлагаются только реальные для этого поколения ленты объёмы (1.5TB/3.0TB), а не общий список всех возможных объёмов.
- **Подсказка по кодам объёма** — в диалоге схемы есть сворачиваемый список, расшифровывающий все двухсимвольные коды объёма, чтобы не приходилось держать их в памяти.
- **Шифрование базы через OpenPGP** — вся база (пароли, заметки, соответствия тегов) шифруется публичным GPG-ключом через GPGME; расшифровать её может только владелец приватного ключа.
- **Пароль от ключа всегда запрашивается заново** — при каждой разблокировке базы GPGME принудительно показывает окно ввода пароля (`pinentry-mode ask`), даже если `gpg-agent` уже закэшировал пароль для других нужд. Это исключает разблокировку базы «по инерции» без явного ввода пароля.
- **Безопасная работа с памятью** — пароли и секретные ключи хранятся в защищённой памяти (`sodium_malloc`) и надёжно затираются (`sodium_memzero`) сразу после использования.
- **Интерфейс на GTK3** с нативным заголовком окна (`GtkHeaderBar`), работает как под Xorg, так и под Wayland без дополнительных настроек.

## Формат тега

Тег состоит из 5 блоков, разделённых дефисами. Порядок блоков задаётся уникальной схемой, сгенерированной для конкретной базы.

Компоненты тега:

| # | Компонент | Описание |
|---|-----------|----------|
| 1 | `type` | Тип физического носителя |
| 2 | `size` | Объём накопителя |
| 3 | `content_tag` | Пользовательская метка содержимого |
| 4 | `cipher` | Алгоритм шифрования |
| 5 | `dsalt` | Уникальная соль диска |

Каждый блок имеет вид `[ЗАКОДИРОВАННОЕ_ЗНАЧЕНИЕ][СОЛЬ]`, где последний символ — не часть данных, а криптографическая соль блока (см. ниже).

### Алгоритм генерации тега

1. **Схема базы.** При создании базы её 5 компонентов перемешиваются в случайном порядке — эта последовательность фиксируется как уникальная схема для данной базы.
2. **Кодирование данных.** Введённые пользователем тип, объём и шифр преобразуются в короткие внутренние коды по словарям утилиты.
3. **Соль диска.** Для каждого носителя генерируется собственная случайная соль (`dsalt`).
4. **Сборка блоков.** Закодированные значения выстраиваются в порядке, заданном схемой базы.
5. **Соль блока.** Для каждого блока вычисляется криптографический символ соли — BLAKE2b от значения блока, секретного `noise_key` базы и глобальной `salt` базы — и добавляется последним символом блока.

### Пример

Тег `HK-T1R-BAM-LK-XYQ` при схеме по умолчанию (`type-size-content-cipher-dsalt`):

| Блок | Код | Соль | Расшифровка |
|:----:|:---:|:----:|:------------|
| `HK` | `H` | `K` | Тип носителя: **HDD** |
| `T1R` | `T1` | `R` | Объём: **1TB** |
| `BAM` | `BA` | `M` | Метка содержимого: **Backup** (пользовательская) |
| `LK` | `L` | `K` | Шифр: **LUKS** |
| `XYQ` | `XY` | `Q` | Соль диска: **XY** |

> Задача кодирования — не скрыть сам факт существования атрибута (объёма, типа), а лишить наблюдателя опорных точек для структурного анализа. Человекочитаемые значения (`500GB`, `HDD`) сразу раскрывают семантику и границы блоков; короткие неочевидные коды в сочетании со случайной перестановкой схемы устраняют эту утечку метаданных.

## Схемы кодирования

**Тип носителя (`type`):** один символ. Обычные накопители — по первой букве: `H` — HDD, `S` — SSD, `U` — USB, `M` — M.2, `D` — SD, `C` — CF, `O` — OPTICAL, `X` — OTHER. Поколения магнитных лент LTO кодируются цифрами `1`–`9` (LTO1–LTO9), и для каждого поколения доступны только реально существующие для него объёмы.

**Шифр (`cipher`):** один символ: `L` — LUKS, `V` — VeraCrypt, `B` — BitLocker, `7` — 7-Zip, `A` — Age, `G` — GPG, `N` — без шифрования (NONE).

## Архитектура и реализация

Diskpass написан на **C** (изначально прототип был на Python, затем полностью переписан для контроля над памятью и производительностью). Используются:

- **libsodium** — генерация случайных значений, безопасное выделение и затирание памяти.
- **GPGME** — управление OpenPGP-ключами и шифрование/расшифровка базы, включая принудительный запрос пароля при каждой разблокировке.
- **cJSON** — сериализация базы данных.
- **GTK3** — графический интерфейс, включая нативный заголовок окна и совместимость с Xorg/Wayland.
